# 0001. 레포를 역할별로 5개(docs / api / web / infra / .github)로 분리한다

> **목적** PM·디자이너·프론트엔드·인프라(AI 에이전트)와 협업하는 "백엔드 개발자"로서 사용자의 작업과 에이전트의 작업을 분명히 구분하고, 무관한 변경이 다른 영역의 배포를 일으키지 않게 한다.
>
> **결정** 레포를 역할별로 5개(docs / api / web / infra / .github)로 분리한다. 모노레포(A)와 api + 나머지 2개 분리(B)는 기각.
>
> **감수한 것** 초기 설정 비용, 공통 규칙의 레포별 반복 적용, api·web 동시 변경 시 PR과 배포가 둘로 나뉨.

## 맥락

이 프로젝트는 사용자가 백엔드를 담당하고, PM·디자이너·프론트엔드·인프라는 AI 에이전트가 맡는 구조다. 프로젝트를 시작하면서 코드와 문서를 어떤 단위의 레포로 둘지 정해야 했다.

결정 시점에 해결하고 싶었던 문제는 두 가지였다.

1. **무관한 변경으로 인한 불필요한 배포.** 레포가 분리되어 있지 않으면 CI/CD에서 무관한 변경(예: 문서나 프론트 수정)이 다른 영역의 배포를 일으킬 수 있다. 이를 막고 싶었다.
2. **백엔드에만 집중하는 협업 구조.** 사용자는 온전히 백엔드에만 집중해 개발하고 싶었다. 자신의 커밋과 에이전트의 커밋이 섞이지 않는 것도 원했다.

고려해야 할 트레이드오프는 "레포가 하나일 때와 나뉘어 있을 때의 **관리 포인트 증가**"와 "**확실하게 구분해서 작업하는 것**" 사이에 있었다.

모노레포에서도 GitHub Actions의 `paths` 필터나 CODEOWNERS로 1번 문제를 해결할 수 있다는 점은 결정 시점에 알고 있었고, 그 방법 자체에 문제가 있다고 보지는 않았다.

## 검토한 대안

| 대안 | 장점 | 단점 | 비고 |
|----|----|----|----|
| A. 모노레포 (레포 1개) | `paths` 필터·CODEOWNERS로 배포 분리와 소유권 구분이 가능하다. api 변경과 web 변경을 PR 하나로 묶을 수 있어 프론트·백엔드 배포 버전 불일치 윈도우를 줄일 수 있다. 빠르게 프로토타입을 만들기에 적합하다. | 사용자의 커밋과 에이전트의 커밋이 한 이력에 섞인다. PR을 검토할 때 사용자가 만들지 않은 코드가 함께 보인다(폴더를 지정해 볼 수는 있지만 그 필터링 자체가 비용). 배포가 따로 된다는 사실이 레포 구조만으로는 보이지 않고 설정을 봐야 안다. | 기각 |

### A. 모노레포에 대한 보충

- `paths` 필터·CODEOWNERS로도 배포 분리가 된다는 점은 인정한다. 그럼에도 기각한 이유는, 레포 분리가 "시작할 때 한 번 설정해 두면 이후에는 신경 쓰지 않아도 되는 방식"이고, "다른 사람이 보더라도 배포가 따로 된다는 것이 바로 보이는 방식"이라고 판단했기 때문이다.
- api PR과 web PR을 하나로 묶을 수 있다는 점은 충분히 매력적이고, 프론트·백엔드 배포 버전 불일치 윈도우를 줄이는 방법인 것도 맞다. 다만 어차피 두 레포를 재배포하는 것이 불일치 윈도우를 100% 제거해 주는 것은 아니다. 그리고 PR이 하나라는 것은 그 PR 안에 사용자의 작업과 프론트 작업이 섞여 있다는 뜻이다. 프론트 작업은 사용자가 하지 않은 것이므로, PR을 검토할 때 사용자가 만들지 않은 코드도 같이 보이는 문제가 있다. 폴더만 지정해서 보는 것이 가능하다는 점은 이번에 알게 됐지만, 그렇게 한 번 따로 필터링하는 것 자체가 비용이라고 지금도 판단한다.

### B. 2개 분리에 대한 보충

- 기각의 중심 근거는 **롤백 단위**다. 에이전트가 작업한 web과 infra가 한 레포에 있으면, 운영에 반영한 뒤 web만 되돌리려 해도 같은 레포에 쌓인 infra 변경까지 함께 되돌아가는 상황이 생길 수 있다. 즉 경계를 넘나드는 커밋이 있으면 롤백이 올바르게 동작하지 않을 가능성이 있다고 판단했다. 이는 결정 시점의 예상이지 실제로 겪은 관찰은 아니다.
- 보조 근거로, 레포를 분리하면 그 레포에 들어가기만 하면 해당 영역의 이력이 별도 필터링 없이 바로 보인다. `git log -- infra/`처럼 경로를 지정해 이력을 볼 수 있다는 점은 결정 당시에는 몰랐지만, 그 점을 알고 난 뒤에도 이 보조 근거는 유지한다.
- 그래서 관심사별로 레포를 나누는 것이 처음에는 귀찮지만 유지보수와 관리에 유리하다고 판단했다.

### docs와 .github를 별도 레포로 둔 이유

- 문서·에이전트 설정·이슈를 infra 레포에 넣으면 레포의 목적이 흐려지고, 문서만 바꿔도 인프라 CI가 반응한다.
- 포트폴리오이므로, 이 프로젝트의 여정에서 있었던 일들을 인사담당자가 코드로 보지는 않을 것이라고 생각했다. 그 내용을 docs 레포에서 몰아볼 수 있게 하고 싶었다.

## 결정

**C. 역할별로 5개 레포(docs / api / web / infra / .github)로 분리한다.**

결정적 이유는 사용자가 **PM·디자이너·프론트엔드·인프라 엔지니어와 협업하는 "백엔드 개발자"로서의 정체성을 분명하게 갖고 개발해 보고 싶었다**는 것, 그리고 **명확한 문서와 규격을 기반으로 한 협업을 경험해 보고 싶었다**는 것이다. 만약 사업 아이템을 검증하는 것이 목적이었다면 모노레포로 빠르게 개발해 프로토타입을 만드는 쪽을 택했을 것이다.

기준의 우선순위를 정리하면 다음과 같다.

- 협업 경계의 명확성(사용자 작업과 에이전트 작업의 분리, 관심사별 롤백·이력 단위) **>** 초기 설정 비용과 공통 규칙 반복 적용 비용
- 협업 경험(문서·규격 기반 협업) **>** 개발 속도(빠른 프로토타입)

선택한 안의 단점에 대해서는, 시작할 때의 설정 비용과 공통 규칙을 각 레포에 반복 적용하는 비용을 제외하면 **개발 도중 발생하는 비용은 거의 없을 것**이라고 판단했고, 그것이 이 안을 고른 이유이기도 하다. api·web 동시 변경 시 PR이 나뉘는 비용은, 모노레포로 묶어도 배포 버전 불일치 윈도우가 완전히 사라지지는 않는다는 점과 PR에 남의 코드가 섞이는 비용을 함께 고려해 감수하기로 했다.

이 결정의 범위는 이 프로젝트의 레포 구성 전체다.

## 결과와 트레이드오프

**좋아지는 것**

- api 레포에는 사용자의 커밋만 남는다. 사용자의 작업 범위가 레포 단위로 드러난다.
- 각 영역의 배포가 따로 이루어진다는 것이 레포 구조만으로 보인다. 별도 CI 설정을 읽지 않아도 된다.
- 관심사별로 롤백 단위가 나뉘고, 각 레포의 이력이 필터링 없이 바로 보인다.

**포기하는 것**

- api 변경과 web 변경을 PR 하나로 묶는 것. 그로 인해 프론트·백엔드 배포 버전 불일치 윈도우를 줄일 기회를 일부 포기한다.
- 모노레포로 빠르게 프로토타입을 만드는 개발 속도.

**새로 떠안는 것**

- 시작 시 레포별 설정 작업.
- 레포 전체에 적용해야 하는 규칙은 레포마다 반복 적용해야 한다. 실제 사례: 2026-10-28, 라벨 7개를 4개 레포에 똑같이 만들어야 했다.
- api·web을 함께 바꿀 때 PR 두 개를 각각 올리고 두 레포를 각각 재배포해야 한다.

**이 결정이 일반화되는 범위**

사용자가 레포 구성을 판단하는 일반 기준은 다음과 같다. **규모가 작고 빠른 결과가 목적이면 모노레포, 규모가 크거나 역할 간 경계가 목적이면 분리.** 이 프로젝트는 규모는 작지만 역할 간 경계가 목적이므로 후자에 해당한다.

API 계약을 어느 레포에서 관리하고 api·web PR을 어떻게 연결할지는 별도 ADR에서 다룬다.

### 재검토 조건

다음 중 하나에 해당하면 이 결정을 다시 본다.

1. 프로젝트의 목적이 "역할 간 협업 경험"에서 빠른 출시·검증으로 바뀌면. 이 경우 유력한 대체 대안은 A(모노레포)다. 사업 아이템 검증이 목적이었다면 처음부터 모노레포로 빠르게 프로토타입을 만들었을 것이기 때문이다.
2. 에이전트 협업 없이 사용자 혼자 전체(web·infra 포함)를 개발하게 되면 이 결정을 재검토한다.
