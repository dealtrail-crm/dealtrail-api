# 트러블슈팅 기록

문제를 어떻게 추적해서 해결했는지 남기는 곳이다.
핵심은 **실패한 가설까지 포함한 과정**이다. 정답만 적힌 기록은 "운 좋게 찾았다"와 구분되지 않는다.

## 작성 기준

다음 중 하나라도 해당하면 기록한다.

- 원인을 찾는 데 가설을 2개 이상 세워야 했던 문제 (첫 가설이 틀린 경우가 특히 가치 있다)
- 원인이 코드 한 줄이 아니라 설계·설정·환경의 조합에서 나온 문제
- 재발 방지를 위해 테스트·설정·규칙을 새로 넣은 문제

오타 수정처럼 보자마자 원인이 보인 것은 기록하지 않는다. 커밋 메시지면 충분하다.

## 파일 이름

```
docs/troubleshooting/NNNN-제목.md
```

- `NNNN`: 0001부터 시작하는 4자리 일련번호. ADR과 별개로 센다. (`0000`은 템플릿 전용)
- `제목`: 현상을 짧게. "버그 수정"이 아니라 "lead-전환-중-실패해도-account가-남음"처럼 증상이 보이게.
- 예: `0001-lead-전환-부분-롤백.md`, `0002-만료-공간-정리-배치-중복-실행.md`

## 작성 방법

본문은 **문답 기반**으로 작성한다. 추적과 해결의 판단은 사용자의 것이고, 에이전트는 문장화만 한다.

1. **가능하면 추적 중에 문답을 시작한다.** 가설을 세울 때마다 사용자가 답을 추가하면 senior-backend가 가설 블록을 하나씩 덧붙인다. 해결 뒤에 되짚으면 틀린 가설은 기억에서 사라지고, 맞은 가설만 "처음부터 알았던 것"처럼 남는다.
2. 메인 Claude가 [`0000-template.md`](./0000-template.md)의 항목 순서로 질문하고, 논리적 빈틈("이 가설을 기각한 근거가 관찰인가 추측인가" 등)을 짚는다. 사용자가 답한다. 템플릿의 `<!-- -->` 주석이 각 항목에서 무엇을 물어야 하는지의 안내다.
3. senior-backend가 템플릿을 복사해 다음 번호로 저장하고, **사용자의 답변만을 근거로** 본문을 쓴다. 답변에 없는 가설·원인·수치를 지어내지 않고, 빠진 부분은 `TODO(질문)`으로 남긴다. 안내 주석은 지우고, 맨 위 요약 블록은 본문을 다 쓴 뒤 마지막에 채운다.
4. 사용자가 검토·수정·승인하고 직접 커밋한다. 관련 이슈와 해결 PR 링크가 들어 있는지 확인한다. 재현 절차·로그는 이슈에, 과정은 여기에.

문서 구조: 제목 → **요약 인용 블록(현상 → 근본 원인 → 해결, 1~3줄)** → 메타 표 → 현상 → 원인 추적 → 근본 원인 → 해결 → 재발 방지. 요약에는 본문에 없는 내용을 쓰지 않는다.
