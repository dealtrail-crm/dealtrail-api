# ADR (Architecture Decision Record)

되돌리기 어렵거나 여러 대안을 저울질한 기술 결정을 남기는 곳이다.
"무엇을 골랐는가"보다 **"왜 다른 것을 버렸는가"**가 기록의 가치다.

## 작성 기준

다음 중 하나라도 해당하면 ADR을 쓴다.

- 되돌리는 비용이 큰 결정 (스키마 구조, 트랜잭션 경계, 격리 방식, 배포 방식 등)
- 대안을 실제로 2개 이상 검토한 결정 (검토했다는 것은 장단점을 비교했다는 뜻이지, 이름만 떠올렸다는 뜻이 아니다)

반대로, 대안이 사실상 하나뿐이거나 내일 바꿔도 비용이 없는 결정은 ADR로 남기지 않는다. 그런 것은 PR 설명이나 커밋 본문이면 충분하다.

## 파일 이름

```
docs/adr/NNNN-제목.md
```

- `NNNN`: 0001부터 시작하는 4자리 일련번호. 비워 두거나 재사용하지 않는다. (`0000`은 템플릿 전용)
- `제목`: 결정 내용을 짧게. 한국어 허용. 공백 대신 `-`.
- 예: `0001-레포-분리.md`, `0002-lead-전환-트랜잭션-경계.md`

## 작성 방법

본문은 **문답 기반**으로 작성한다. 결정과 판단은 사용자의 것이고, 에이전트는 문장화만 한다.

1. 결정 **직후**에 시작한다. 구현이 끝난 뒤 되짚으면 "당시에 몰랐던 것"이 사라지고 결정이 실제보다 당연해 보인다.
2. 메인 Claude가 [`0000-template.md`](./0000-template.md)의 항목 순서로 질문하고, 논리적 빈틈("이 대안은 왜 검토하지 않았나", "관찰인가 추측인가" 등)을 짚는다. 사용자가 답한다. 템플릿의 `<!-- -->` 주석이 각 항목에서 무엇을 물어야 하는지의 안내다.
3. senior-backend가 템플릿을 복사해 다음 번호로 저장하고, **사용자의 답변만을 근거로** 본문을 쓴다. 답변에 없는 근거·대안·수치를 지어내지 않고, 빠진 부분은 `TODO(질문)`으로 남긴다. 안내 주석은 지우고, 맨 위 요약 블록은 본문을 다 쓴 뒤 마지막에 채운다.
4. 사용자가 검토·수정·승인하고 직접 커밋한다. 관련 이슈·PR 링크가 들어 있는지 확인한다. 날짜가 찍힌 이력이 사후 작성이 아니라는 근거가 된다.

문서 구조: 제목 → **요약 인용 블록(목적/원인 → 결정 → 감수한 것, 1~3줄)** → 메타 표 → 맥락 → 검토한 대안 → 결정 → 결과와 트레이드오프(재검토 조건 포함). 요약에는 본문에 없는 내용을 쓰지 않는다.

## 상태 변경

- 결정이 뒤집히면 기존 파일을 고치지 않는다. 새 ADR을 쓰고, 기존 파일의 상태를 `대체됨 (→ NNNN)`으로 바꾼다.
- 기존 ADR의 "재검토 조건"에 걸려서 다시 검토했다면, 새 ADR의 맥락에 그 사실을 적는다. 조건을 미리 적어 둔 것이 실제로 작동했다는 증거가 된다.
